# Local cloud sync adapter (v1)

Run `python -m hermes_cli.cloud_sync` with one JSON object on stdin. Stdout is
exactly one JSON response; diagnostics go to stderr. Input and output are bounded
to 32 MiB. No tokens or credentials are accepted. Native passes its trusted,
account-isolated absolute `home` and `ui_root` paths on every call.

Common request: `{"version":1,"action":"prepare|apply|status|read_blob","home":"/absolute/account/home","ui_root":"/absolute/account/ui"}`.
Errors: `{"ok":false,"error":{"code":"invalid_request|sync_failed","message":"..."}}`
(exit 1). Successful responses have `ok:true`.

## prepare

Additional request fields: `request_id` (UUID, newly generated by native for a new
exchange; reuse it for transport retry), optional `device_id` (nonempty string,
1–128 characters; omit to use the durable generated installation UUID).
Response:

```json
{"ok":true,"request_id":"UUID","exchange":{"version":1,"device_id":"UUID","after":"0","limit":50,"operations":[]},"uploads":[{"sha256":"64 hex","size":123}],"status":{"state":"synced","pending":0,"cursor":"0","issues":[]}}
```

`exchange` is sent verbatim to POST `/api/v1/desktop/sync/exchange` after all
`uploads` have been read with `read_blob` and succeeded at PUT `/api/v1/desktop/sync/blobs/:sha256`. Persisted
preparations return identical operations/cursor/uploads on retry after restart.
Only one unapplied preparation is active: another request ID returns that active
preparation's request ID (native MUST echo the returned ID to apply). A transport
failure leaves the preparation pending. There are at most 16 operations per
exchange and 50 changes per page. Status issues identify blocked conversations
and unavailable media; blocked snapshots are never acknowledged as uploaded.

## apply

Additional request fields: `request_id` exactly as returned by prepare,
`response` (the unwrapped HTTP response `data`: `cursor`, `has_more`, `results`,
`changes` from the design), optional `blobs` array as `{sha256,data_base64}`. Supply one downloaded blob per call; validated blobs accumulate durably, including across process restart.
Response:

```json
{"ok":true,"request_id":"UUID","changed_session_ids":[],"changed_profile_ids":[],"pending_downloads":[],"has_more":false,"status":{"state":"synced","pending":0,"cursor":"12","issues":[]}}
```

Missing media leaves the exchange pending; `pending_downloads` lists SHA256s native
must GET and supply in another apply with the same request ID and response. Busy
or unknown execution likewise leaves the exchange pending and cursor unchanged.
Once complete, reapplying the identical response is a no-op. Reusing its request ID
with a changed response, unknown IDs, mismatched operation results, backwards
cursors, malformed revisions, or invalid hashes fail without acknowledging work.
A preparation remains durable until all of its changes apply. Native should retry
pending application before preparing another exchange.

`status` needs no additional fields; response is `{"ok":true,"status":{...}}`.
Status states are `synced`, `pending`, or `blocked`; `pending` counts durable
outbox operations and unapplied preparations; `issues` is an array of objects
with `code`, `key`, `message`. Native maps transport failures to offline status.

## Portable documents

Keys are `conversation/<profile>/<root-id>`, with profile `default` or a safe named
profile within this account home. Payload:
`{"schema":1,"profile":{"id":"default","metadata":{},"config":{}},"segments":[...SessionDB export rows...],"attachments":[]}`.
Messages include UIDs and archival flags. Compression segments retain parent IDs.
Model settings, names and descriptions are allowlisted; machine paths, credentials,
execution ownership, pending runtime actions and approval grants are excluded.
Conflicts get deterministic new IDs and titles suffixed ` (sync conflict)`.
Remote media is materialized privately under `<home>/cloud-sync/media/<sha256>`;
portable references use `cloud-blob:<sha256>`. Missing or oversized owned local
attachments block that snapshot rather than silently losing files.

## read_blob

Additional request: `sha256` from a prepared upload descriptor. Response:
`{"ok":true,"sha256":"64 hex","data_base64":"..."}`. Each blob is at most
8 MiB. Native reads and uploads one at a time. Prepared operation JSON is bounded
to 12 MiB, independently from attachments; one conversation may carry many blobs.

Initial scanning visits local conversation metadata in a SQLite read transaction;
the durable outbox is capped at16 documents/12MiB and remaining work keeps status
pending until subsequent exchanges;
it does not hold a writer lock while serializing history or hashing files.
Unchanged portable hashes are not queued. Writer transactions protect publication
and all inbound history changes. The initial implementation prioritizes complete
change detection; very large histories can make polling expensive.

Completed local response receipts retain the most recent 128 exchanges. An evicted
request ID is rejected by apply, with no state changes; the server's operation-ID
receipts and tombstones remain permanent. Pending preparation, pending response,
outbox operations and per-conversation acknowledged revisions are never evicted.

The blob cache remains `<home>/cloud-sync/media/<sha256>`. Restored display references
use `<sha256>.<extension>` in that same private directory; extensions are derived
from verified file magic (PNG, JPEG, GIF, WebP, PDF, MP3, WAV, Ogg, MP4), and unknown
bytes use `.bin`. No remote filename chooses the destination. Attachments are
recognized in structured media content, attachment arrays, serialized tool-result
JSON, Markdown links/images, desktop image-reference wrappers, and MEDIA/@file
references. Tool-call arguments and ordinary text filesystem mentions are history,
not automatic file reads. Supported local sources are the owning home's dedicated
media/attachment/upload directories and known media caches, or the explicit UI
attachment/media/upload directories. Arbitrary project files outside those stores
are not implicitly uploaded.

New imports increment a durable per-session cloud generation. Warm resume and the
existing pre-submit/pre-turn history reconciliation reload model context only at
the next idle boundary; a running conversation is deferred by SessionDB's lease,
compression and admission guards. Local crash markers and execution state never
travel in the document. Restored default-home settings remain device-local; model
choice is retained in each conversation, and named profiles carry allowlisted
model/name/description metadata.
