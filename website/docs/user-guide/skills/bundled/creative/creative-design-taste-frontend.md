# Design Taste Frontend Skill

Create a considered visual system that fits the actual product, audience and material. This MIT-based Aino adaptation carries the taste and quality workflow without the upstream asset kit, random-dealing scripts, host hooks or automated finish gate.

## When to Use

- A website or interface looks generic, assembled or inconsistent.
- A brief needs art direction, typography, hierarchy and a coherent component system.
- Refine a real application while preserving its layout, functional boundaries and approved palette.

## Prerequisites

- Current product screens, source, approved references and truthful content where available.
- Use `read_file` and `search_files` for existing tokens, components, assets and area instructions; `patch` and `terminal` for implementation.
- Use available `desktop_preview`, `drive_preview` or `browser_exec` for rendered validation.
- `image_generate` is optional and requires a configured provider. Use licensed supplied assets first. This bundle includes no stock-image/icon collection, browser binary or upstream gate scripts.

## How to Run

1. Classify the surface as a task interface, reading surface, marketing page or showcase.
2. Write a short direction grounded in real product truth: audience, main task, content, tone and constraints.
3. Define one type/color/spacing/icon system and the page's composition before editing.
4. Build the meaningful interaction, then examine the real rendered result.
5. Fix incoherence, inaccessible states and visual drift before claiming completion.

## Procedure

### Begin with truth
Inspect the existing application before drawing a replacement. List current actions and their destinations. Distinguish content the user supplied, facts verified from source, and prototype fixtures. Never invent reviews, customers, prices, success statistics or personal contact details.

Identify the medium: a desktop task interface benefits from precise density, stable geometry and immediate feedback; a launch page may need a stronger authored composition. Do not impose full-viewport marketing sections or mandatory hero animation on settings, conversations, dashboards or mobile text.

### Establish one system
Follow [references/design-system.md](https://github.com/NousResearch/hermes-agent/blob/main/skills/creative/design-taste-frontend/references/design-system.md). Reuse existing semantic tokens and components when the brief calls for compatibility. Choose a compact type scale, clear measure, equal content edges and a restrained radius/shadow vocabulary. Treat button hit area, icon optical size and interaction state as part of the same component specification.

Create hierarchy with content, alignment and type before introducing cards or badges. Vary composition when the material earns it rather than repeating identical icon-heading-paragraph blocks. Keep the primary action obvious. Shared dividers need one owner and common insets across adjacent surfaces.

### Use material deliberately
Show the actual subject: a tool's real workflow, the actual product, the place or the content. Use a licensed stand-in only when needed and identify it in delivery notes. Do not present stock imagery as the user's real product or personnel. Preserve true third-party logos and their licensing; UI icons should form one coherent family.

Generated artwork may support the direction when asked, but should not replace functional controls or accurate product screenshots. Avoid generic gradients, random 3D ornaments or excessive glass that do not help the task. A distinctive existing palette, including purple, remains valid when approved; this adaptation does not impose an arbitrary color ban.

### Write and animate with intent
Apply [references/copy-and-feedback.md](https://github.com/NousResearch/hermes-agent/blob/main/skills/creative/design-taste-frontend/references/copy-and-feedback.md). Use concrete nouns and action labels; write errors with a useful recovery. Do not rewrite approved facts to make a composition fit.

Motion should communicate state and continuity. Provide hover, focus, press and disabled feedback without forced movement on every element. Avoid scroll-jacking, unstable text baselines and gratuitous entrance sequences in task tools. Honor reduced motion and retain an already-visible readable state.

### Inspect and repair
Check the first viewport, middle and end, open menus/panels and error/empty states. Use the actual window sizes and a narrow layout; include 200% zoom when practical. Verify images load, text stays readable, edges align, controls fit, focus is visible and primary actions update the correct state. Profile expensive effects when they visibly stutter.

Compare against the approved reference with a written mismatch list. Fix material differences or explain intentional functional exceptions. Report manual/browser/project-test checks accurately; do not print a fictional upstream `GATE: PASS`.

## Pitfalls

- Applying a landing-page formula to an operating application.
- Randomizing the user's palette or replacing real content to satisfy a style rule.
- Importing the upstream 36 MB asset kit or third-party imagery without reviewing its separate licenses.
- Repeated card grids, weak type hierarchy, inconsistent icons, noisy outlines or too many simultaneous accents.
- Finishing from source inspection without looking at the rendered page when browser access is available.

## Verification

Verify functional interactions and visual coherence separately. Include tested screens/states, viewport sizes, representative long content, keyboard/reduced-motion checks and reference comparisons. Identify stand-ins and unavailable integrations. This adaptation provides the workflow locally; it does not claim the official Taste scripts or automated checker ran.
